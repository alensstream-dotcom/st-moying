## 0.1.35：恢复独立素材库、Roll 与批量预览

上一版把“替换素材数据”做成了“删掉素材操作”，本版恢复需要的功能。导航恢复 **素材库**，包含 **同人角色 / 服装素材**；两类素材都可以独立生成预览，不需要角色档案，不绑定剧情人物。“套用”仅是可选操作。

### 角色数据与按作品分类

- Animadex 官方仓库明确指向 [Laxhar/noob-wiki](https://huggingface.co/datasets/Laxhar/noob-wiki) 作为同源 CSV。使用其公开 `danbooru_character.csv`，不需要账号令牌，不抓取网站整库图片，也不绕过官方导出权限。**这是公开同源数据快照，不等于 Animadex 当前实时图库列表，更不代表 NAI 认识每个角色。**
- 原始 244,932 行，按源 character 标识与作品归组，保留 239,378 个主条目、22,273 个作品分组；同作品且确有本体的 5,554 个括号版本合入本体。主条目保留原 trigger，已合并版本的原始 trigger 保留为别名。跨作品同名不强并；无法可靠判定的别名可在详情手动合并为一个人物。
- 作品、角色、trigger 可搜索，未知作品类型仍有独立作品分组；源数据多数是英文原名，不假称已全部翻译中文。保留常见中文别名，可手动编辑；“LLM 定位中文名（一次）”只发送搜索词，模型提供候选后必须匹配本地目录，未匹配不伪装成库中结果，不自动保存或生图。
- 默认女性筛选来自源标签，仅用于目录；可能误标，可在详情修正，生成不额外注入该性别标记，也不据此改写剧情人物。Role/Work/Trigger 分开存储，CSV 导入保留原 trigger。
- 目录作为约 7.7MB 的独立本地 JSON 文件按需读取，不塞进每楼提示词、不每楼请求外站。列表分页、作品侧栏只绘制匹配前 100 项，预览本机懒加载；个人编辑/删除状态保存在 IndexedDB，基础目录不反复复制进 localStorage。数据来源、源文件 SHA256 与构建脚本见 `scripts/build-material-catalog.py`、`src/data/characterCatalog.json` 和 `THIRD_PARTY_CHARACTER_CATALOG_LICENSE.txt`。

### 入口与操作

1. **浏览与 Roll**：选作品/分类、搜索或 Roll 当前范围。同人 Roll 优先来源数较多的条目，不自动付费；服装还可以在详情“Roll 配色”，只替换词表已收录的颜色标签，不改版型，不调用 LLM。
2. **详情页**：点素材名称或 trigger 进入详情；可编辑名称、作品、标签，复制、保存、删除、导入自己的预览图。新素材可直接预览，角色套用不是前置条件。
3. **预览放大**：卡片图片双击打开灯箱，详情同样支持双击与 Enter。改标签后仍展示旧图，并标注预览待更新，不把旧图冒充新标签的生成结果。
4. **排队生成**：当前页、勾选素材、筛选结果三种范围，可设每批上限（1–1000，默认 24），显示任务数再由用户点击。详情范围为单项，可直接生成或重 Roll 图；默认沿用当前/素材库生图预设，可以选择预设、NAI 模型覆盖、构图和间隔，不修改剧情生图配置。
5. **串行队列**：不并发请求，至少间隔 3 秒；默认只跳过“标签相同且已有图”的素材，勾选重画可重 Roll。切页继续、可追加、可停止并取消当前请求；连续 3 次失败停下。停止/重开用独立任务代次，旧请求不能污染新队列；重复点击同一项不会重复排入当前任务。刷新/关页会停止，已完成图片保留，下一次可补齐。
6. **导入导出**：同人支持官方 character/copyright/trigger CSV、JSON 素材数组、个人编辑备份；可以导出当前排队范围或个人编辑。服装支持新版备份、`[{"name":"白衬衫黑裙","tags":"white shirt, black skirt"}]` 简单数组，自动去掉同名同标签重复导入，新增项默认不参与剧情自动召回，编辑确认后再开启。标签备份不包含图片，图片可通过灯箱下载或逐项导入。

### 旧数据

按用户要求移除旧素材待整理与旧备份入口。打开素材库后清理旧素材元数据、旧归档和已退役的服装/脸型/姿势预览键；保留新版个人编辑和预览，不触及剧情图片、人物定妆、历史穿脱账本和已经套用的标签快照。素材数据与剧情人物分离，切换或修改人物不改动素材本身。

未运行测试，未调用付费 LLM/NAI。完成类型检查、静态数据核对和发布构建；实际酒馆操作、图像效果及渠道兼容性由用户验证。队列只在用户点击后开始，不因打开目录、导入或刷新自动生成。

## 0.1.34：用新衣橱替换旧素材库

导航中的“素材库”已替换为 **角色与衣橱**，只保留 **服装衣橱 / 同人角色** 两个入口；角色管理中的定妆与穿搭复用同一套组件。

### 衣服怎么固定

- 删除旧服装长句模板与扩展表（wardrobeExtra / wardrobeKarama / wardrobeCapsules），撤掉旧在线索引与 Danbooru 图片接口组件。旧脸型、体型、姿势候选退出自动素材召回，设置页同步清理对应入口，不保留两套并行 UI。
- 新衣橱内置 **38 套搭配、594 个常用衣物标签**，按古风仙侠、奇幻、日常、校园、职业、礼服、家居、泳装、内搭、鞋袜配饰分类。标签从有出处的 Danbooru 索引逐项核对，使用 `white shirt, collared shirt, long sleeves, black skirt, pleated skirt` 这样的独立词组，不再拼形容词长句。标签数据来源与 MIT 许可见 [原项目](https://github.com/DominikDoom/a1111-sd-webui-tagcomplete) 和 THIRD_PARTY_TAGS_LICENSE.txt。
- **这不是 NAI 官方完整白名单，也不承诺完全复现图片。** [NAI 官方文档](https://docs.novelai.net/en/image/tags/)说明标签建议用于查看模型熟悉的词。未收录词会显著标出并阻止保存，不静默删除；用户已在 NAI 核对的衣物词可主动补入个人词表，明确标为用户确认，随新版衣橱备份导出。
- 操作：选款或新建 → 添加/删除标签 → 可选“试穿一次（NAI）” → 收藏这套 → 选择剧情人物 → “穿给人物”。试穿只生成一张，沿用当前 NAI 配置，不开启图片参考；已存的参考/试穿图本地懒加载，可放大查看。
- 首次穿搭或原文明示换装时，现有剧情分析请求可以从允许自动使用的新衣橱里选候选；正文明确服装优先于候选。已有衣服则原样继承，不能因为每楼没提款式就重新随机挑。自动候选按时代元数据及原有文化冲突规则过滤；手动指定继续可覆盖剧情时代。
- 款式标签保存在衣橱；给人物穿上后，绑定存到指定楼层。扣子解开、衣袖滑落、裙子掀起等仍由每楼衣物账本保存。袖长、领型等附着到衣物，鞋袜单品合并已有穿搭，避免删除上衣后还留下独立“袖子”。没有穿好或换装证据就沿用状态；“始终使用整套”模式会按用户选择忽略剧情穿脱。

### 描述或图片怎么变成款式

“从描述或参考图建立新款式”可选择插件中已保存的 LLM 渠道，**主动点击才请求一次**。图片需 PNG/JPEG/WebP、8MB 内，并要求渠道支持 OpenAI 兼容图片输入。只识别衣物，输出受本地词表约束的独立标签；结果进入编辑器，需检查/收藏/穿给人物，不自动采用、不循环重试、不回退到其他模型。图片只发送给用户选择的渠道，不默认发给 NAI，不保存进文本请求历史。剧情每楼不会额外调用这个识别功能。

外部二次元换装库和服装搭配图库作为找参考的链接，**不是已经接通的图片 API**。不批量抓取或重新分发这些网站的原图。

### 同人角色

内置常用角色按“作品类型 → 所属作品 → 角色”浏览，固定身份只使用“角色名＋作品名”，不抄入示例图的衣服、画师或外貌长串。可填中文名/别名、随机挑选当前范围角色、作为定妆候选或固定给所选人物。完整角色目录支持 Animadex 官方 `character,copyright` CSV 与新版 JSON 导入，使用 IndexedDB 保存，未知作品类型保留“未分类”。Animadex 原站作为认人入口，未假称跨域图库已连接；[官方导出方式](https://github.com/zetaneko/AnimaDex/blob/main/docs/import-from-site.md)需要用户自己的导出授权。

### 旧数据与验证范围

旧个人收藏原始数据与图片缓存保留；新衣橱初次打开会归档旧服装，列入“旧服装待整理”，不会自动注入。旧描述可放入整理栏逐条重建，也可导出旧原始备份。历史楼层、已绑定套装、角色原有档案不被批量删除；**已有角色如需换成新标签，请从新衣橱“穿给人物”一次**。新版衣橱备份包含款式与个人补充词，角色身份目录单独备份；图片仍是本机缓存，不包含在标签备份中。

按用户要求未运行测试，也未调用付费 LLM/NAI。完成类型检查、静态数据核对和发布构建；酒馆内操作、各渠道图片识别兼容性和实际生成效果交由用户验证。

## 这一版改了四个人物一致性问题

年龄、素材库开关都能在「设置 → 自动 tag → 素材库」里调，不用改代码。

1. **年龄段不再糊成一片、也不再画成老太太**：角色档案多了「年龄段」字段（child / teenager / young adult /

   素材库的候选也按年龄段区分，同楼里四个年龄段画成同一个年纪的情况不会再出现。

2. **同人骨相终于进得来，而且能按外形精确还原**：以前「注入人物外貌候选」默认关，同人条目永远排在
   脸型/体型后面挤不进去。现在默认开；正文点名作品名或角色名时那条同人**直接排第一**。
   更要紧的是外形：正文把角色写成「银白长发、紫瞳、尖耳」这种具体样子、而你库里正好有一条逐项对得上时，

   想稳中还是把姓名写进正文，别指望外形词。
3. **同职业不再撞衫**：服装召回会在同分之间摇号（同一楼内固定，换楼换一批），提示词里也加了
   「不同的人不许穿同一件」和按廓形区分的硬要求。素材库补了 60 条廓形差别明显的款式，

4. **该特写就特写**：新增景别判据。正文写到阴蒂/穴口/乳头/手指/唇眼时该给 close-up，
   写到胸/腰臀时该给 upper body 或 cowboy shot，只有交代位置关系时才用 full body。

### 景别参照表

| 正文正在写的东西 | 该用的景别 | 常见错法 |
|---|---|---|
| 阴蒂、穴口、插入处 | close-up / lower body | 拍全身，部位只有一个点大 |
| 乳头、乳晕、乳房形状 | close-up / upper body | 拍全身 |

| 腰、臀、大腿根、胯部动作 | cowboy shot / lower body | 拍全身 |
| 姿势与两个人怎么接触、谁在上面 | full body 或 medium | — |
| 房间、站位、谁在门口 | full body / wide shot | 只剩脸，看不出空间关系 |

判据是**这一句的看点在哪一层**：看点是一个具体部位就收到那一层，整楼的图不许全在远景。
收景别时要把 body / 全身相关的 tag 一起收掉（否则模型还是按全身构图），
特写也别把眼睛裁出镜头。现在远景不会再被当成「有效构图」放过去。

## 这一版改的是画面准不准

   不许删人；人数按画面里的身体数，不按有没有露脸。
2. **道具必须带落点**：毛笔在阴部写字，就写 `brush on pussy`，不许一手 `brush` 一手 `pussy`
   各飘一个 tag——分开写模型只会画一支支着的毛笔和一个裸体。道具、接触、方向都绑成词组落。
3. **先概括再写 tag，但不写多**：落 tag 前先用一句话说清「谁·用什么·在哪个部位·做什么·对方什么反应」，
   这句写不出来的格子不许画。tag 控制在 25～40 个，同一个意思不重复，形容词不叠三层，
   只留在画面上有形状的东西。写得多不等于写得准，塞满反而互相稀释。
4. **衣服不再乱飘**：新增跨楼服装账本。每楼把每个人「穿着什么、脱到哪一步」记在楼层里，
   下一楼直接注入成【服装现状】并当作既成事实——当前楼没写衣着就照抄，不再每层从零挑一套。
   同一楼内更不会换，脱离源就是「每层随机挑」。
5. **半脱固定成独立状态**：露肩、露背、露臀、掀裙写成 off shoulder / slipped down / pulled aside /
   skirt lifted / clothes around waist，衣服留在身上被画出来。只写 nude 会变光人，只写整套衣服又变没脱。
   账本里有半脱却画成全裸、账本里已经脱了又穿回整身，都会被判错并重试。

服装账本跟着楼层走，删楼或换 swipe 会自然失效；角色档案里的 outfit 仍是「她的常态衣橱」，
两者分工是「这场戏此刻穿到哪」对「她平时穿什么」。

## 被渠道拦、被截断的时候

先说清管辖范围：**破限挡位与「破限附加词」只作用于出图这条副 API 请求，不进正文生成**。
正文是 SillyTavern 主 API 生成的，插件塞不进任何提示词——正文被拦时调挡位没有用，那是渠道层的事。

能管的是出图请求。两件事分开说。

**一、被拦。** 拦截不认授权话术：过滤查的是请求与响应**文本本身**，提示词越露骨越容易被整条掐掉。
所以：

1. 拦截变成可判定的事：`finish_reason=content_filter`、空回复、或一段「抱歉，这段内容…」的客气话，
   都会被单独定性成「被渠道内容过滤拦下」，不再混在「解析失败」里。
2. 命中就降载重试：下一次改发兼容版——系统提示里的露骨示例词换成中性占位
   （`brush on <部位>`、`液体 on <部位>`），思考块压到 5 行并只保留最小结构。字段值本身不变。
3. 平时就少露骨：`<thinking>` 里改用英文 tag 短词描述身体与接触，不写中文长句。

真正被拦死了（连兼容版都过不去），出路只有换一个宽一点的渠道，或者把出图请求指到另一个模型上。

**二、被截断。** 「JSON 未闭合（差 6 个收尾括号）」说明输出被腰斩在写某张图的中途。旧版整份丢掉重发，
可重试只是让它「写短点」——图数不减，输出的主体成本没降，照样在同一处被切，于是反复失败。现在：

1. **先救，不重发**：从后往前找第一个还能闭合的位置，把尾巴补成合法 JSON。已经写完的那几张图
   是好的，救回几张就发几张，比整楼一张都没有强。
2. **救不动才重试，并且这次砍图数**：本楼压到最少张数（没设下限就压到 1），先保证交得出完整 JSON。
   少的那张回头再补，比整楼空白容易得多。

顺带说一句：**破限附加词恢复叠加**。它和档位是叠加关系（档位在前、附加词在后），留空时用内置默认那段；
选「关闭」只发附加词。上一版把它整段吃掉了，所以「开到极限也没用」——真正在起作用的那份根本没发出去。
